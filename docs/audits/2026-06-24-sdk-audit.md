# Node SDK Audit Report — `@zincapp/znvault-sdk` v4.1.1

## 1. Executive Summary

The SDK is **functionally unreliable across multiple core feature areas** despite being a published, zero-dependency package consumed by other ZincApp projects. The dominant failure mode is **SDK↔server contract drift**: request bodies use field names/casing the server never reads (so writes are silently dropped or rejected with 400), and response types declare keys the server never sends (so reads resolve to `undefined`). The KMS crypto path is broken in both directions, several auth methods (login-with-2FA, change-password, force-change-password, 2FA verify) are 100% non-functional, and one finding (CONTRACT-01 SSO introspection) nulls out `tenantId` for downstream resource servers. Crucially, **no security/tenant-isolation hole was found**, credential handling is clean, and the bugs fail loudly (400/404) or softly (`undefined`) rather than leaking data.

**Counts by adjusted severity:** Critical 1 · High 14 · Medium 13 · Low 13 · Info 6 (note: two distinct findings share the id `CONTRACT-01` and two share `KMS-02`-adjacent ids; they are reported separately below).

## 2. Findings by Severity

### CRITICAL (1)

#### KMS-01 — KMS encrypt/decrypt/re-encrypt use the wrong ciphertext field name
- **File:** `src/kms/client.ts:114-136`, `src/types/index.ts:701-711,724-728`
- **What's wrong:** The server names the encrypted blob `ciphertext` on both request and response; the SDK sends/reads `ciphertextBlob`. `decrypt()` omits the required `ciphertext` → 400. `encrypt()`/`generateDataKey()` responses are typed `ciphertextBlob`, always `undefined` at runtime. Convenience helpers `encryptString`/`encryptBuffer` return `response.ciphertextBlob` (undefined); `encryptBuffer` then `Buffer.from(undefined)` throws.
- **Why it matters:** The entire KMS crypto capability of the SDK is broken in both directions — a core advertised feature.
- **Fix:** Rename the field to `ciphertext` in `DecryptRequest`/`EncryptResponse`/`GenerateDataKeyResponse` and in the request bodies for decrypt/re-encrypt/generate-data-key-without-plaintext; update `encryptString`/`decryptString`/`encryptBuffer`/`decryptBuffer` accordingly.

### HIGH (14)

#### KMS-02 — KMS `reEncrypt()` sends `keyId`/`ciphertextBlob` instead of `sourceKeyId`/`ciphertext`
- **File:** `src/kms/client.ts:122-136`
- **What's wrong:** Server expects `{ ciphertext, sourceKeyId?, sourceContext, destinationKeyId, destinationContext }`. SDK sends `keyId` (no such field) and `ciphertextBlob` (no such field); required `ciphertext` is missing → every `reEncrypt()` call fails with 400. The method signature exposes no `sourceKeyId` param at all.
- **Why it matters:** `reEncrypt()` is dead on arrival.
- **Fix:** Send `{ ciphertext, sourceKeyId, sourceContext, destinationKeyId, destinationContext }`; type the response as `{ sourceKeyId, destinationKeyId, ciphertext }`. (Shares root cause with KMS-01 — fix together.)

#### KMS-03 — KMS `context` is required server-side but optional in the SDK
- **File:** `src/kms/client.ts:106-144`, `src/types/index.ts:698,710,721`
- **What's wrong:** `context` (and `sourceContext`/`destinationContext`) are required `Type.Record` on the server; the SDK types them optional and passes `undefined`, which axios/JSON drops → 400. The common case (`encryptString(keyId, plaintext)` with no AAD) fails at runtime.
- **Why it matters:** Breaks the documented-optional encrypt/decrypt/generate-data-key public API.
- **Fix:** Make `context` required in the SDK types, or default it to `{}` in the client methods before POSTing. (Underlying defect is arguably server-side — `context` probably should be `Type.Optional`; flag to the server team.)

#### KMS-04 — KMS `getKey`/`getKeyByAlias` returns an all-`undefined` object (response nested under `keyMetadata`)
- **File:** `src/kms/client.ts:31-37`
- **What's wrong:** `GET /v1/kms/keys/:keyId` returns `{ keyMetadata: {...} }`; the SDK casts the body to a flat `KmsKey`, so `key.keyId`, `key.state`, etc. are all `undefined`. Field names also differ (`keyState`/`createdDate`/`keyUsage` vs `state`/`createdAt`/`usage`).
- **Why it matters:** `getKey`/`getKeyByAlias` are effectively broken.
- **Fix:** Unwrap `response.keyMetadata` and map `keyState`→`state`, `createdDate`→`createdAt`, `keyUsage`→`usage`.

#### KMS-06 — KMS `setRotationStatus` sends `rotationEnabled`/`rotationPeriodDays`; server expects `enabled`/`intervalDays`
- **File:** `src/kms/client.ts:80-89`
- **What's wrong:** Server validates `{ enabled (required), intervalDays? }`. SDK sends `{ rotationEnabled, rotationPeriodDays }` → required `enabled` missing → 400. Even if it passed, the interval would be ignored.
- **Why it matters:** A published method (toggle auto-rotation) is 100% non-functional.
- **Fix:** Send `{ enabled, intervalDays }`; update `getRotationStatus`'s return type to use `intervalDays`.

#### SECRET-01 — Secrets `updateMetadata` hits a non-existent path with the wrong body
- **File:** `src/secrets/client.ts:63-72`
- **What's wrong:** SDK PATCHes `/v1/secrets/:id/meta/data` with `{ tags, ttl_until, expires_at }`. The real route is PATCH `/v1/secrets/:id/metadata` and accepts only `{ tags }`. Wrong path → 404; `ttl_until`/`expires_at` aren't in the schema/handler even on the correct path.
- **Why it matters:** Fully-broken public method (404 on every call).
- **Fix:** Use PATCH `/v1/secrets/:id/metadata` with `{ tags }` only; drop `ttlUntil`/`expiresAt` (or move them to PUT `/v1/secrets/:id`).

#### AUTH-01 — `login()` sends `totp_code` but server expects `totpCode`
- **File:** `src/auth/client.ts:50-54`
- **What's wrong:** The server reads `totpCode`; the SDK sends `totp_code`, so for any 2FA-enabled account the handler hits `if (!totpCode)` → 401 "2FA code required" regardless of the code supplied. `login()`/`loginWithTenant()` can never complete for MFA-enabled users.
- **Why it matters:** Silently breaks the primary auth path for all MFA-enabled accounts (MFA is recommended for admins). Fails closed.
- **Fix:** Send `totpCode`. (Same mismatch also in `disable2fa()` at client.ts:239 — fix too.)

#### AUTH-02 — `changePassword()` sends snake_case; server requires `currentPassword`/`newPassword`
- **File:** `src/auth/client.ts:115-120`
- **What's wrong:** SDK posts `{ current_password, new_password }`; required camelCase fields absent → 400 before the handler runs. Same defect in `forceChangePassword()` (see AUTH-03).
- **Why it matters:** Core auth method completely broken (deterministic 100% failure).
- **Fix:** Send `{ currentPassword, newPassword }`.

#### AUTH-03 — `forceChangePassword()` sends `username` + snake_case and mistypes the return
- **File:** `src/auth/client.ts:122-132`
- **What's wrong:** Server requires `{ userId, currentPassword, newPassword }` and returns `{ message }`. SDK sends `{ username, current_password, new_password }` (all three required fields missing → 400) and types the return as `LoginResponse` (no tokens are returned).
- **Why it matters:** The recovery path when `password_must_change` blocks login is 100% broken.
- **Fix:** Send `{ userId, currentPassword, newPassword }`; type the return as `{ message: string }`.

#### AUTH-04 — `verify2fa()` sends `{ code }` but server expects `{ totpCode }`
- **File:** `src/auth/client.ts:232-234`
- **What's wrong:** Required `totpCode` missing → 400; 2FA can never be verified/enrolled via the SDK.
- **Why it matters:** Fully breaks the advertised 2FA-setup feature.
- **Fix:** Send `{ totpCode: code }`.

#### AUTH-06 — `getApiKey()` reads `response.apiKey` but the route returns the key object directly
- **File:** `src/auth/client.ts:176-179`
- **What's wrong:** `GET /auth/api-keys/:id` returns the bare public key object (`toPublic(apiKey)`), not a `{ apiKey }` envelope (unlike list/create). `response.apiKey` is `undefined`.
- **Why it matters:** Public method always returns `undefined`.
- **Fix:** Return the response directly (it is already the `ApiKey` object).

#### AUTH-08 — `createManagedApiKey()` POSTs to a non-existent route with the wrong body shape
- **File:** `src/auth/client.ts:259-269`
- **What's wrong:** `/auth/api-keys/managed` has only a GET. There is no POST create-managed route. Managed keys are created via POST `/auth/api-keys` with a nested `managed: { rotationMode, rotationInterval, gracePeriod, ... }` block. SDK POSTs flat fields to the wrong path.
- **Why it matters:** Public method non-functional (wrong path AND wrong body).
- **Fix:** Create via POST `/auth/api-keys` with `{ name, permissions, managed: { rotationMode, rotationInterval, gracePeriod } }`; remove the bogus POST.

#### CONTRACT-01 (SSO) — SSO introspection nulls out `tenantId` (and risks `clientId`) on valid tokens
- **File:** `src/sso/types.ts:25-54`, `src/sso/client.ts:407-428`
- **What's wrong:** The server `/oauth/introspect` returns RFC 7662 **snake_case** (`tenant_id`, `client_id`, `token_type`). The SDK declares/reads only camelCase, so `ValidatedToken.tenantId` is set to `undefined` via `response.tenantId!`. `clientId` is recovered by the `?? response.aud!` fallback; `tenantId` has no fallback. The token is attached to `req.ssoUser` by `createFastifySSOAuth`/`createExpressSSOAuth`.
- **Why it matters:** Downstream resource servers authorizing on `req.ssoUser.tenantId` read `undefined` for **every valid token**, defeating per-tenant authorization in consumer apps. This is the closest thing to a security-relevant defect in the SDK.
- **Fix:** Read snake_case fields: declare `tenant_id`/`client_id`/`token_type` (or accept both) and parse `response.tenant_id ?? response.tenantId`, `response.client_id ?? response.clientId ?? response.aud`. Consider failing closed (return `null`) when `tenantId` is missing. Add an integration test asserting `ValidatedToken.tenantId` is populated.

#### BINARY-01 — `getKrl()` corrupts binary KRL payloads (response accumulated as a UTF-8 string)
- **File:** `src/http/client.ts:472-490` (read path); `src/ssh-ca/client.ts:108-113` (consumer)
- **What's wrong:** `executeRequest` does `let data = ''; res.on('data', c => data += c)` with no `setEncoding`, coercing each Buffer chunk to UTF-8. Non-UTF-8 bytes become U+FFFD, permanently destroying the original bytes. The server sends the OpenSSH KRL as raw `application/octet-stream` binary; `getKrl()`'s `Buffer.from(data, 'binary')` cannot recover already-lossy-decoded bytes (verified: `[0x00,0xff,0x80,0xc3,0x28]` → `[0x00,0xfd,0xfd,0xfd,0x28]`).
- **Why it matters:** A corrupted RevokedKeys file makes sshd reject it or silently fail to revoke certificates — a revocation-bypass consequence. (`secrets.downloadFile`/`certificates.download` are safe — those are base64-in-JSON.)
- **Fix:** Accumulate response bodies as Buffers (`chunks: Buffer[]` → `Buffer.concat`); `.toString('utf8')` only for the JSON/text path. Add a `responseType: 'buffer'`/`requestRaw` option so `getKrl` receives real bytes. The dead `Buffer.isBuffer(data)` guard shows the buffer path was intended.

#### RETRY-01 — Non-idempotent POSTs are retried on 5xx and network errors
- **File:** `src/http/client.ts:379-438`
- **What's wrong:** The retry loop is method-agnostic. The 4xx guard only short-circuits 400–499; 5xx and `statusCode 0` (timeout/connection) fall through and retry (up to 4 attempts). The classic "request committed server-side but response lost (502/503/timeout)" race silently double-applies mutations: duplicate KMS key versions (`POST /v1/kms/keys/:id/rotate`), duplicate API-key rotations, redundant key creation/schedule-deletion. No idempotency-key handling exists server-side.
- **Why it matters:** Silent duplicate side effects across a broad set of mutating operations.
- **Fix:** Only auto-retry idempotent methods (GET/PUT/DELETE/HEAD); never retry POST/PATCH unless an explicit idempotency key is sent. At minimum, don't retry POSTs on network/timeout errors.

#### PKG-01 — Publish workflow runs no tests, lint, or typecheck
- **File:** `.github/workflows/publish.yml:27-34`
- **What's wrong:** The only workflow (on `v*` tags) does checkout → `npm ci` → `npm run build` (tsup/esbuild, no type-checking) → `npm publish`. No `npm test`/`lint`/`typecheck`, no PR-triggered CI. A release with type errors or broken behavior builds and publishes cleanly. The repo's own CLAUDE.md/RELEASING falsely claim "Runs tests on PRs."
- **Why it matters:** Zero automated quality gates before publishing a public SDK — this is precisely how the contract drift above shipped undetected.
- **Fix:** Add `npm run typecheck` (highest value — tsup won't catch type errors) and `npm run lint` as required steps before publish, plus a PR-triggered CI workflow. Add unit tests once TEST-01/TEST-03 land. Correct the docs.

#### ROTATION-01 — Failed managed-key rotation permanently stops auto-rotation
- **File:** `src/http/client.ts:320-377`
- **What's wrong:** In `doManagedKeyRefresh`, `scheduleManagedKeyRefresh()` runs only on the success path (inside `try`, after the `await`). A single transient bind failure (5xx/network blip) rejects, `finally` resets `isRefreshing` but arms no new timer; the timer callbacks `.catch` and notify but don't reschedule. Auto-rotation dies for the process lifetime; the key later expires and every request 401s. (No leak — old key retained.)
- **Why it matters:** Silent-onset auth outage with no self-recovery, triggered by a transient error.
- **Fix:** Wrap the refresh in try/catch/finally and always reschedule a (backed-off) retry timer even on failure, so transient errors self-heal before grace/expiry.

#### SSO-CACHE-01 — Introspection cache extends effective token lifetime
- **File:** `src/sso/client.ts:139-168`
- **What's wrong:** On a cache hit, `validateToken` returns the cached response without re-checking the token's own `exp`. A token expiring shortly after first introspection stays "active" for up to the cache TTL (default 60s); a server-side revoke isn't seen until the entry expires (unless `invalidateCachedToken` is called).
- **Why it matters:** Bounded authorization-window weakness for resource servers using the middleware — a conventional caching trade-off, but worth tightening.
- **Fix:** On cache hit, re-validate `response.exp` against `Date.now()` (treat as expired/`null`); cap cache TTL at `min(configuredTtl, exp - now)`. Document TTL as max staleness for revocation; default lower for high-security deployments.

#### TEST-01 — `npm test` hard-fails with connection errors on a machine with no live server
- **File:** `vitest.config.ts:2-5`; `test/test-config.ts:207-209`; `.env:3`
- **What's wrong:** Integration suites gate on `isIntegrationEnabled()` = `process.env.ZNVAULT_BASE_URL !== undefined`, but `vitest.config.ts` loads the committed-locally `.env` which sets `ZNVAULT_BASE_URL`. A fresh clone's `npm test` runs the suites and they fail with `Connection error`. (`.env` is gitignored, so local vs CI behavior diverges; no CI test workflow exists — see PKG-01.)
- **Why it matters:** DX/CI ergonomics — no green test suite without standing up the full stack.
- **Fix:** Gate on an explicit opt-in flag (e.g. `RUN_INTEGRATION=1`) not auto-populated by `.env`, or don't load `.env` by default. Adopt the graceful skip pattern from `ssh-ca.test.ts` across the other integration files.

#### TEST-03 — No unit tests for KMS, Certificates, SSO, Superadmin, Health, Audit, Roles, Policies, Tenants clients
- **File:** `src/kms/client.ts`; `src/certificates/client.ts`; `src/sso/client.ts`; `src/sso/middleware.ts`; `src/superadmin/{auth,index}.ts`
- **What's wrong:** Only `ssh-ca.test.ts` (and `from-env.test.ts` for auth providers) has server-independent unit tests. KMS (~24 methods incl. encrypt/decrypt/data-keys), Certificates (18 methods), and SSO client+middleware (a separately published subpath) have **zero** tests of any kind; integration coverage is skip-gated and unreachable in CI.
- **Why it matters:** The contract drift above (KMS-01–08, AUTH-01–08, CONTRACT-01) is exactly what mocked-HttpClient unit tests would have caught.
- **Fix:** Add mocked-HttpClient unit tests (mirroring `ssh-ca.test.ts`) for at least KMS, Certificates, SSO client+middleware, and Superadmin — asserting request path/method/body shaping and response parsing. These run in CI with no server.

- **Fix:** Drop those fields from `create` and call `setRotationStatus` separately, or document that rotation is configured post-creation.

#### SECRET-04 — `list()` sends a `tags` query param the server doesn't accept
- **File:** `src/secrets/client.ts:88` — `tags` isn't in the querystring schema; tag filtering silently does nothing (over-fetches, no error).
- **Fix:** Remove the `tags` query param, or add server-side tag filtering.

#### AUTH-09 — `rotateApiKey()`/`rotateCurrentApiKey()` send unread `expiresInDays`
- **File:** `src/auth/client.ts:197-201,221-225` — `RotateApiKeyBody = { name? }`; rotation recomputes expiry from the old key's original duration. The param is a misleading dead value.
- **Fix:** Drop `expiresInDays`, or add server support; document that rotation keeps the current duration.

#### HEALTH-01 — `HealthStatus.status` enum and `checks` shape don't match the server
- **File:** `src/health/client.ts:5-15` — server uses `'ok'|'degraded'|'error'` and `checks: { db, tls, kmip? }`; SDK uses `'healthy'|'degraded'|'unhealthy'` and `{ database, encryption, kms }` (never populate).
- **Fix:** Align `status` to `'ok'|'degraded'|'error'` and `checks` to `{ db, tls, kmip? }`.

#### URL-01 — KMS alias path params are not URL-encoded
- **File:** `src/kms/client.ts:35-37` — `getKeyByAlias` interpolates the alias raw; a `/`, `?`, `#`, or `%` alters the request path. (The finding's second cited sink, `updateKeyAlias`, is a false positive — that alias is in the JSON body.) Not a server-side auth bypass.
- **Fix:** Wrap alias in `encodeURIComponent` in `getKeyByAlias` (matching the secrets client); add a unit test with `/` and `?`.

#### TLS-01 — `NODE_TLS_REJECT_UNAUTHORIZED=0` disables verification SDK-wide (HttpClient honors it, SSOClient doesn't)
- **File:** `src/http/client.ts:122-124` — secure-by-default is preserved, but `HttpClient` honors a process-global Node flag (an operator may set it for an unrelated host), while `SSOClient` uses `?? true` and ignores it.
- **Fix:** Default to `true` regardless of the env var (only explicit `config.rejectUnauthorized=false` disables), or emit a one-time warning. Align `HttpClient` and `SSOClient`.

#### TIMEOUT-01 — Only an idle/socket timeout exists; no overall request deadline
- **File:** `src/http/client.ts:461-524` — `socket.setTimeout` is inactivity-based; a slow-trickle response can hang far past `timeout`. No `res.on('close'/'aborted')` and no wall-clock deadline (the abrupt-RST leak is largely theoretical on modern Node).
- **Fix:** Add an absolute deadline timer (`req.destroy()` + reject, cleared on settle); handle `res.on('aborted')`/`req.on('close')`. Consider a response size cap.

#### PARSE-01 — Non-JSON 2xx body is silently returned as a string cast to `T`
- **File:** `src/http/client.ts:481-492` — on `JSON.parse` failure, `resolve(data as T)` hands callers a raw string; a contract violation (HTML error page, truncated body) surfaces deep in business logic as `undefined`.
- **Fix:** For JSON endpoints, reject with a clear `ZnVaultError` ('Invalid JSON response from server') on parse failure of a non-empty body; distinguish expected-empty (204/void) via Content-Type.

#### MANAGEDKEY-01 — `isRefreshing` early-return fabricates a `ManagedKeyBindResponse` with empty fields
- **File:** `src/http/client.ts:325-341` — a concurrent `refreshManagedKey()` gets a synthetic object with `id:''`, `prefix:''`, `expiresAt:''`, `permissions:[]` (the `key` field is the real working key). Persisting/logging that metadata records bogus data.
- **Fix:** Single-flight: store the in-flight `Promise<ManagedKeyBindResponse>` on state and return it to concurrent callers; don't fabricate empty fields.

#### MANAGEDKEY-02 — Far-future rotation delay overflows setTimeout's 32-bit limit → busy loop
- **File:** `src/http/client.ts:284-315` — a `nextRotationAt` > ~24.8 days makes the delay overflow, firing in ~1ms; bind returns the same `next_rotation_at`, so it reschedules with the same overflowing delay → fast busy loop hammering the bind endpoint (server caps interval at 365 days, so this is reachable).
- **Fix:** Clamp delay to `min(delay, 2_147_483_647)` and re-evaluate on fire; reschedule far-future rotations in chunks.

#### RETRY-02 — Unclamped `Retry-After` causes a (bounded) multi-day blocking sleep
- **File:** `src/http/client.ts:421-425` — `error.retryAfter * 1000` is taken verbatim from the header with no clamp; `Retry-After: 999999` blocks the caller ~11.5 days. (The title's "loops indefinitely / not counted against attempts" is wrong — the `continue` advances the loop counter.)
- **Fix:** Clamp `Retry-After` to a sane max (e.g. `min(retryAfter, 60s)`); validate `parseInt` is finite/positive.

#### TYPE-01 — `TenantsClient.get` uses a dead `{ success, data }` unwrap
- **File:** `src/admin/tenants.ts:30-37` — server returns a bare `Tenant`; the unwrap branch never triggers and the inline comment is factually wrong (the public signature is already `Promise<Tenant>`).
- **Fix:** Drop the unwrap and the union HTTP type argument.

#### TYPE-02 — Inconsistent list-response handling across clients
- **File:** `src/admin/users.ts:58-77`, `src/admin/roles.ts:53-60`, `src/audit/client.ts:44-56`, `src/secrets/client.ts:98-103`, `src/ssh-ca/client.ts:144-149,181-186` — some methods return `PaginatedResponse<T>`, others unwrap a single key to a bare array; no consistent convention. (The "drops pagination" claim is false for the SSH endpoints — the server emits no pagination there; the `getHistory` break belongs to CONTRACT-04.)
- **Fix:** Adopt one convention — paginated endpoints return `PaginatedResponse<T>`, truly unpaginated lists return `T[]` — and document it.

#### NAMING-01 — `ListRegistrationTokensResponse` uses `tokens`, not the standard `items`
- **File:** `src/types/index.ts:361-363` — the SDK faithfully mirrors the server (the route really returns `{ tokens }`), but that deviates from the documented "Always items" standard. Cosmetic; the endpoint works.
- **Fix:** Where the server already returns `{ items }`, fix the SDK type; where it genuinely returns `tokens`/`entries`, file a server standards bug. Keep wrapper-key naming consistent.

#### OPT-01 — `Secret.createdAt`/`updatedAt` typed required but several endpoints omit them
- **File:** `src/types/index.ts:498-499` — `Secret` is reused as the return of create/get/getByAlias/update/rotate/updateMetadata; 4 of 7 projections omit or snake_case these timestamps, so `secret.updatedAt` is `undefined` despite the `string` type.
- **Fix:** Mark them optional, or (better) normalize the server endpoints to emit camelCase `createdAt`/`updatedAt` consistently. Consider a narrower `SecretMeta` type for projections that omit fields.

#### EXPORT-01 — `AuditStats` exported with no producing method and a shape that doesn't match the server
- **File:** `src/types/index.ts:913-918` — dead public type; the server's stats are `{ successCount, failureCount, uniqueUsers }` and aren't surfaced by the SDK.
- **Fix:** Add a method returning a server-aligned `AuditStats`, or remove the misleading type.

#### EXPORT-02 — Health types double-defined; exported `HealthCheck` is orphaned

#### TEST-02 — Inconsistent unreachable-server handling across integration files
- **File:** `test/ssh-ca.test.ts:254-314` vs `test/integration.test.ts:20-42`, `test/auth.test.ts:10-15`, `test/from-env.test.ts:444` — only ssh-ca skips gracefully on `CONNECTION_ERROR`/`TIMEOUT`; the others throw.

- **No data-corruption or auth-bypass defects:** Every functional bug fails loudly (400/404) or softly (`undefined`); none silently mis-writes data or grants unauthorized access.
